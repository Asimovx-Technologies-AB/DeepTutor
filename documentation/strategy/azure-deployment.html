DeepTutor on Azure

The platform currently spans Render, Netlify, Vercel, Neon, Pinecone, AWS and Google AI. This plan puts the infrastructure in one Azure resource group per environment, provisioned by Terraform and deployed by GitHub Actions — and does it for roughly the price of two coffees a week.

The recommendation

Run the API on Container Apps (Consumption), the SPA on Static Web Apps Free, and — the load-bearing choice — use one PostgreSQL Flexible Server (B1ms) with pgvector as the relational database, the vector index and the knowledge-graph store.

That one decision collapses three paid-or-soon-paid services (Neon, Pinecone, and the local disk the graph store is quietly losing data on) into a single ~$16/month resource. It is the difference between a dev environment at ~$25/month and one at ~$100.

§3 Two calls worth arguing about

Scale-to-zero versus always-warm

api_min_replicas = 0 is the dev default and makes compute effectively free, at the price of a 10–20 second cold start on the first request. If a warm endpoint matters more than the money, note the arithmetic: Container Apps at min_replicas = 1 costs about $33/month — more than App Service Linux B1 at ~$13. If always-warm becomes permanent, moving the API to App Service is the cheaper answer, and it is a contained change to one Terraform file. Scale-to-zero is right until somebody asks otherwise.

Azure AI Search was considered and rejected

It is the obvious "Azure vector database", and its Basic tier is $75/month — three times the entire rest of this environment. The Free tier caps at 50 MB and one service per subscription, which will not hold a textbook corpus. pgvector on a server that has to exist anyway is both cheaper and simpler. Revisit AI Search when semantic ranking becomes a product differentiator rather than an infrastructure line item.

§4 What will break

Reading the application code turned up six things that would turn a clean terraform apply into a broken environment. Four are handled or worked around in the Terraform; two need application changes.

Graph data is lost on every deploy

Handled

GraphKVStore writes entities, relations and triplets as JSON to local disk. Container Apps replicas are disposable, so every revision would discard the knowledge graph. An Azure Files share is now mounted at /data/lightrag — no code change, loss stopped. The real fix is Postgres JSONB, in phase 3.

Uploads land on disposable disk

Handled

Same treatment: /data/uploads is an Azure Files share. Separately, MAX_UPLOAD_SIZE_MB is set to 5000 — Container Apps ingress will not carry a 5 GB upload in one request and gunicorn would time out first. Nobody has hit it because nobody has tried.

The image cannot drop ChromaDB yet

Worked around

A new slim multi-stage Dockerfile drops docling, easyocr and torch, taking the image from multiple GB to well under one — which is what makes a 0.5 vCPU replica and a fast cold start viable. ChromaDB could not go with them: vector_store.py imports it at module scope and six API modules import that at their own module scope, so it loads on every boot even though Pinecone is the active backend. Making those imports lazy is a small change with a real payoff.

/health bills an LLM call per probe

Worked around

The health endpoint calls Gemini and then queries the database. Wired to a container probe at 15-second intervals, that is roughly 5,700 Gemini calls a day for a health check. The probes therefore point at /, which returns static JSON. The right fix is to split the route: a no-I/O /health/live, a DB-only /health/ready, and the expensive view kept for humans.

CORS is open to * and the env var is ignored

Blocking

main.py sets allow_origins=["*"]. Terraform passes a correct CORS_ALLOWED_ORIGINS to the container and nothing reads it. This must be fixed before the environment is shared with anyone outside the team. It is a five-line change, and the one item here that is genuinely security-relevant.

The SQLite fallback hides a Postgres outage

Blocking

A Postgres connection failure is caught and silently swapped for a local SQLite file. On a disposable container that means an outage produces a working-looking API writing user data to a disk that is about to vanish. In a deployed environment this must raise; keep the fallback behind an explicit local-dev flag.

§5 Terraform, not Bicep

Either would work. Terraform, for four reasons:

It is not Azure-only. S3, Pinecone, Neon and Netlify all have providers. The migration window is months, not days, and the same tool can describe the resources that have not moved yet. Bicep can only ever describe the Azure half.

plan is a genuine review artifact. The plan workflow posts it on the PR, so a reviewer sees "3 to add, 1 to change, 0 to destroy" before approving.

State is explicit — a versioned blob you can inspect, lock and roll back, rather than deployment history inferred from a resource group. And the sovereign-bundle direction in the product strategy implies non-Azure targets eventually; Terraform keeps that door open.

The cost is honest: an extra tool, a state file to protect, and provider version drift. The bootstrap script enables blob versioning and 30-day soft delete on the state container, which turns state corruption from a rebuild into a two-minute restore.

Verification status, stated plainly: the configuration has not been run against a live subscription — there is no Azure CLI or Terraform binary in the dev environment. The plan workflow (fmt → init → validate → plan) is the gate, and it runs on this branch's first PR. Expect one or two provider-schema fixes on the first pass; that is what the gate is for.

§6 Migration path

Phase 1 ships an environment that runs the app exactly as it is today. Nothing is rewritten to get it live — that is deliberate, and it is what keeps the first deploy a one-day job instead of a two-week one.

Phase 1 — this branch ~2 days

Lift onto Azure

Deploy the resource group. The backend keeps Gemini, Pinecone and S3; DATABASE_URL points at the new Flexible Server. Azure Files mounts stop the graph-data loss. Retire Vercel; keep Netlify until the Static Web App is proven, then delete all three config files. Exit proof: a push to main reaches a working URL with no human step, and a deliberate restart loses zero data.

Phase 2 ~2 days

S3 → Azure Blob

s3_store.py is a clean, self-contained class. Add a Blob equivalent behind the same interface, authenticating with the managed identity already in place, and copy the bucket with azcopy. Removes the AWS bill and the last long-lived access key.

Phase 3 ~3 days

Graph KV → Postgres JSONB

Replace per-topic JSON files with a graph_kv table holding JSONB. The store already has a narrow interface, so this is a backend swap, not a redesign. Fixes concurrent writes and Azure Files latency in one move. This is also when the ARQ worker and a queue become worth provisioning — not before.

Phase 4 — the real work ~1 week

Pinecone → pgvector

PineconeVectorStore is ~550 lines and does more than store vectors: BM25 sparse search, RRF fusion, page-filtered lookups, namespaces. Postgres answers each piece — HNSW for dense, ts_rank_cd for sparse, the fusion arithmetic ported as-is — and having both in one engine makes hybrid retrieval a single SQL statement instead of two round trips. Re-run the RAGAS suite; the existing retrieval numbers are the acceptance gate.

Decision, not a phase disabled

Azure OpenAI

The module exists and is off. Enabling it is nearly free — S0 is pay-per-token — but switching embeddings changes the vector dimension and forces a full re-index of every document. Two defensible positions: keep Gemini, or move chat to Azure OpenAI for data residency and leave embeddings alone. Do not switch both at once, and never during phase 4.

Open questions, before the first apply

  1. Is there an existing Azure subscription and tenant, or does one need creating? A free trial's $200 credit covers roughly seven months of this environment.
  2. Central India is the primary region because DeepTutor targets Indian users. Static Web Apps uses East Asia because India is not an available deployment location for that service; static assets are delivered through its global edge network and the SPA holds no personal data.
  3. Does the first environment need to be always-warm for demos? That is the $0-versus-$33 decision in §3.
  4. Who owns the Entra app registration for OIDC? It needs User Access Administrator for the first apply, which is more than a typical developer holds.
